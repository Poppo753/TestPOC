Ognuno degli item della checklist è verificato per **presenza sul codice attuale** e
associato ai finding rilevanti in `register.json`. La verifica esaustiva (call graph,

codice attuale e classificarla per severità di remediation.

## Metodo

Per ogni item, evidenza a 2 livelli:
- **CODE** — grep/read verificato di persona (comando riportato + risultato).
- **REF** — riferimenti ai finding autorevoli in `register.json` che documentano il problema.

Legenda dei simboli:
- ✅ verificato presente + confermato non risolto
- ⚠️ verificato presente ma già affrontato altrove
- ❓ non ancora verificabile senza altri strumenti (fuzz, formal)

## Checklist §S1.5

### 1. Withdrawal clamp + burn completo

- **Status:** ✅ Confermato non risolto.
- **CODE:** `contracts/Liquiditymanager.sol:329-346`
  ```
  if (newBalance < netWithdraw) {
      netWithdraw = newBalance;
  }
  ...
  proxy.burn(msg.sender, _shares);
  ```
- **REF:** `CORE-003` (severity critical, confidence high).
- **Impatto:** LP burn shares complete ricevendo meno del valore atteso, senza revert e senza rimborso.
- **Priorità remediation:** Sprint 0 blocker.

### 2. Emergency selector / path

- **Status:** ✅ Confermato non risolto.
- **CODE:** `contracts/ProxyGeneral.sol` — `grep "function emergencyTransfer"` → solo `emergencyTransferAll(address)` a L.459. Nessuna implementazione di `emergencyTransfer(address,uint256,address)`.
- **REF:** `CORE-001` (severity critical), `IFC-001` (duplicato), `CORE-010` (sweep incompleto), `NEW-018` (backdoor drain una volta fixato CORE-001), `NEW-010` (flag executed anche se transfer falliti).
- **Impatto:** emergency withdraw non funziona sul path standard; una volta corretto CORE-001, `NEW-018` diventa attivo e crea rug potential.
- **Priorità remediation:** Sprint 0 blocker + attenzione alla sequenza dei fix (fixare CORE-001 e NEW-018 nella stessa PR).

### 3. First-depositor + donation attack

- **Status:** ✅ Confermato non risolto (nessuna protezione presente).
- **CODE:** `contracts/Liquiditymanager.sol` — `grep` per `firstDeposit|MINIMUM_LIQUIDITY|_decimalsOffset` → 0 match. `grep` per `minLpTokensOut|minLPOut|minShares` → 0 match.
- **REF:** `NEW-001` (share inflation), `NEW-002` (sandwich deposit), `NEW-003` (NAV inflation via donazione di token secondario), `NEW-026` (deposit rounding senza minLpTokensOut).
- **Impatto:** attaccante può inflaziare NAV via `transfer` diretto e diluire depositi successivi. Classico attack vector di ERC-4626 senza minimum liquidity.
- **Priorità remediation:** Sprint 0 blocker. Fix architetturale (virtual shares OZ v5 ERC4626 OR minimum liquidity Uniswap V2 style + tracked balance).

### 4. NAV token/Lens fail-open

- **Status:** ✅ Confermato non risolto — root aggregato in `VALUATION-001`.
- **CODE:** `contracts/ValueCalculator.sol:261-270` (silent zero on token failure), `contracts/adapters/EulerLensAdapter.sol:882` (isCircuitBreakerActive selector fake).
- **REF:** `VALUATION-001` (root); subfindings: `CORE-049`, `NEW-028` (duplicato), `CORE-052` (legacy Euler fallback), `PLG-037` (HF mask con max), `IFC-010` (selector inesistente), `ADP-003` (circuit breaker inerte), `CORE-075` (reserve ratio pre-swap totalValue).
- **Impatto:** deposit/withdraw normali proseguono con NAV parziale; emergency dipende dallo stesso NAV.
- **Priorità remediation:** Sprint 0 blocker. Semantica economica → HUMAN GATE §1.4 prima di implementare.

### 5. Morpho HF scale + Lens/plugin consistency

- **Status:** ✅ Confermato non risolto — bug replicato in plugin E lens.
- **CODE:** `contracts/plugins/MorphoPlugin.sol:1009` `return (collateralValue * params.lltv) / (debtAssets * WAD);` — divisione extra per WAD, HF ritornato in scala 1 invece che 1e18. Stessa formula in `contracts/adapters/MorphoLensAdapter.sol:178`.
- **REF:** `PLG-005` (plugin), `NEW-007` (lens — stessa root cause, sub-finding di PLG-005).
- **Impatto:** `openLeverageAtomic` revert sempre con default MIN_HEALTH_FACTOR = 1.05e18; dashboard monitoring mostra posizioni sane come "liquidazione imminente".
- **Priorità remediation:** Sprint 0 blocker. Rimuovere `* WAD` dal denominatore; allineare a `SharesMathLib` ufficiale Morpho (con VIRTUAL_ASSETS/SHARES — `ADP-039`).

### 7. Timelock / batch / parameter execution

- **Status:** ✅ Confermato non risolto — 3 bug indipendenti nella stessa area.
- **CODE:** `contracts/ParameterManager.sol` — 2 override di `executeParameterChange` (L.250 string, L.498 uint256). Il secondo (interfaccia-compliant) è dead code (`isActive` guard sempre falso).

### 8. Interface selector incompatibili a runtime

- **Status:** ✅ Confermato non risolto.
- **CODE:** `ProtocolManager.sol:320,351,402,414` chiama `ILendingProtocol(plugin).borrow(tokenCode, amount)`; `MorphoPlugin.sol:340,379` implementa solo `borrow(collateralCode, loanCode, amount)`. Selector diversi.
- **REF:** `IFC-004` (root), + IFC-010 (isCircuitBreakerActive), + tutti gli event drift (`IFC-002`, `IFC-005`, `IFC-006`, `IFC-008`, `IFC-009`, `IFC-013`, `IFC-042`), + missing `override` (`IFC-022`, `IFC-023`, `IFC-024`).

- **Priorità remediation:** Sprint 0-1. Riconciliazione firma `ILendingProtocol` two-token per Morpho. Dichiarare `is IX` su ogni impl e aggiungere `override` mancanti.

### 9. Sequencer Uptime Feed e oracle states

- **Status:** ✅ Confermato non risolto.

### 10. Upgrade / storage semantics reali del Beacon

- **Status:** ✅ Confermato non risolto.
- **CODE:** `contracts/Beacon.sol:109` `updateImplementation` — nessun timelock, nessun `migrateFrom` in nessun modulo core.
- **REF:** `CORE-058` (no timelock), `NEW-005` (beacon-lookup senza migrate — root cause architetturale).
- **Impatto:** upgrade di un modulo stateful (SwapManager, ParameterManager, TokenManager, ecc.) fa perdere TUTTO lo storage runtime.
- **Priorità remediation:** Sprint 0-1. Decisione architetturale → HUMAN GATE §1.4 (Opzione A: documentare come "beacon-lookup, non-upgrade" e vietare updateImplementation su moduli stateful; Opzione B: implementare migrateFrom; Opzione C: migrare a UUPS ERC-1967).

### 11. Reentrancy con token/callback avversario

- **Status:** ⚠️ Parzialmente verificato — servono PoC.
- **CODE:** `ProxyGeneral.sol` importa `ReentrancyGuard` ma **nessuna** funzione usa `nonReentrant`. Verificato di persona con grep — 0 hit sul modifier applicato.
- **REF:** `NEW-004` (import senza uso), `CORE-013` (performSwapAuto no nonReentrant), `CORE-073` (ProtocolManager no ReentrancyGuard), `CORE-074` (emergencyWithdraw no guard + flag post-loop), `PLG-025` (UniswapV3PluginDirect no ReentrancyGuard), `PLG-046` (flash-loan callback no nonReentrant), `PLG-115` (guard su callback via boolean flag).
- **Nota critica dalla checklist §S1.5:** "Verificare reentrancy con token/callback avversario, non per assenza modifier." — La reentrancy come **exploit** richiede PoC con ERC777 malicious token. Come **safety net** l'aggiunta di `nonReentrant` è comunque best practice.
- **Priorità remediation:** Sprint 1 dopo PoC. NON aggiungere `nonReentrant` ovunque cieco (§1.4 e §S9.1 vietano fix indiscriminati); prima call graph + PoC + guard al boundary corretto.

## Gate umano che si applica alla remediation

Per **ogni** item Sprint 0 con categoria in {`solvency`, `emergency`, `math`, `access-control`, `governance`, `upgrade`}, l'implementazione del fix rientra nel §1.4 checklist ("applicare una modifica core che cambia NAV, share, fee, prelievo o recovery senza decisione registrata"). Prima di scrivere codice production:
1. l'agente scrive test rosso (regression),
2. l'agente propone la semantica del fix in `security/DECISIONS.md`,
3. **l'utente conferma la semantica**,
4. solo dopo l'agente applica il fix minimo,
5. l'agente verifica che il test rosso diventi verde,
6. l'agente aggiorna register.json con `state=fixed-pending-verification`,
7. la chiusura a `closed` richiede full suite + reviewer.

Per Sprint 1 con categoria in {`oracle`, `slippage`, `mev`}, il fix è tecnico ma comunque impattante: applica la stessa procedura.
