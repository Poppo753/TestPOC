### Blocker C1-09 — encode-packed-collision in SwapManager (SLIT-005..011)

**Finding:** SLIT-005, SLIT-006, SLIT-007, SLIT-008, SLIT-009, SLIT-010, SLIT-011 — tutti in `contracts/SwapManager.sol`, 7 call sites di `keccak256(abi.encodePacked(spendTokenCode, receiveTokenCode))`.

**Root cause:** `abi.encodePacked` con 2+ argomenti di tipo dinamico (string, bytes) produce collisioni: `packed("AB","CD") == packed("ABC","D") == packed("A","BCD")`. Se un attaccante registra un token con codice manipolato, può forzare `pairHash` a collidere con un pair diverso.

**Impatto:**
- `swapSuccesses[pairHash]++` e `swapErrors[pairHash]++` sono usati per statistiche/analytics.
- Non causa perdita fondi diretta (i counter non gated financial decisions).
- Ma: se in futuro il pairHash viene usato per gate condition (es. "solo pair con >100 success possono avere leverage"), la collisione diventa exploit path.

**Test rosso:** `test/foundry/unit/SwapManagerEncodePackedCollision.t.sol`
- Setup: registrare due token pair collidenti (`("AB","CD")` e `("ABC","D")`).
- Eseguire swap sulla prima coppia con successo.
- Asserzione: `swapSuccesses` **NON** deve incrementarsi per la seconda coppia.
- **Attesa pre-fix:** test FALLISCE (i counter collidono).

**Semantica proposta:**
Sostituire ovunque:
```solidity
bytes32 pairHash = keccak256(abi.encodePacked(spendTokenCode, receiveTokenCode));
```
con:
```solidity
bytes32 pairHash = keccak256(abi.encode(spendTokenCode, receiveTokenCode));
```

`abi.encode` produce output size-prefixed che elimina la collisione.

**Impact operativo:**
- Il valore hash cambia → i counter `swapSuccesses`/`swapErrors` esistenti si "azzerano" (i mappings sono per-hash, quelli vecchi restano orfani).
- Non è distruttivo per fondi utente.
- Documentare in release notes.

**Trade-off:** minimo. `abi.encode` costa ~50 gas in più per chiamata a causa del padding. Trascurabile in path swap che costano decine di migliaia di gas.

**Priorità:** Sprint 0 blocker (facile fix, no cambio API, 7 site changes identici).

## Ciclo 4b — Governance policy da decidere

### GOV-DEC-01 — Fee-on-transfer base asset (SLIT-019)

**Finding:** SLIT-019 — `LiquidityManager.deposit` asserisce `balance == pre + net` (strict equality).

**Contesto:** questa asserzione è **correttamente strict** — protegge da bug contabile. Ma se il base asset è un token fee-on-transfer (es. una versione futura di USDT che introduce transfer fee, o alcuni token esotici), l'asserzione fallisce sempre → **DoS totale** di deposit per quel token.

**Cosa serve decidere (utente):**
- **Opzione A**: **policy no-FoT** esplicita. Il base asset deve NON essere fee-on-transfer. Se lo diventa in futuro (upgrade token esterno), pool è pausato + migrazione. → **Nessun fix di codice** ora, solo documentazione.
- **Opzione B**: rewrite deposit invariant come `balance >= pre + net - tolerance` con tolerance parametrizzabile. → **Cambio API deposit**, mint shares su `actual received` non su `amount richiesto`.

**Trade-off:**
- Opzione A: più semplice ma frágile se base asset cambia comportamento.
- Opzione B: più robusto ma cambia l'esperienza utente (potrebbero ricevere meno shares del previsto).

**Priorità:** Sprint 2 (governance decision). Non blocca Sprint 0.
